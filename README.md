# lib_copilot

도서관에서 새 책에 **청구기호(852 ▼h)** 를 매기는 일을 돕는 사서-AI 협업 에이전트.

**쉬운 책은 자동으로 끝내고, 판단이 갈리는 책만 사람에게 넘긴다.**

---

## 왜 만드나

새 책이 들어오면 사서가 청구기호를 매긴다. 이 번호가 곧 책이 꽂힐 자리다.

이 일에는 성격이 다른 두 문제가 섞여 있다.

**① 반복적이다.** 매 권마다 같은 검색을 손으로 되풀이한다 — 업체 번호를 본교에서 확인하고, 타대학 분포를 보고, 다시 본교로 돌아와 맞춰본다. → **자동화한다.**

**② 일관되지 않다.** 판단이 사서의 암묵지에 기대 있어 사람마다 갈린다. 실제로 사서가 처리한 12권 중 **4권이 작성자가 매긴 번호를 교열 담당자가 뒤집었다**:

| 책 | 작성자 | 교열 최종 |
|---|---|---|
| 부린 왕자 | 179.9 (자기계발) | **332.6324** (부동산투자) |
| 일리아스 좋아하세요? | 883 (그리스문학) | **028.9** (독서) |

둘 다 틀리지 않았다. 같은 책을 어느 관점에서 보느냐의 문제다. → **판단이 갈리는 지점에만 사람이 개입한다.**

그래서 이 도구는 "정답을 맞히는 기계"를 목표로 하지 않는다. **확실한 건 답 하나로 끝내고(①), 갈리는 건 후보와 근거를 함께 내놓고 사서에게 넘긴다(②).**

## 어떻게 도는가

> ⚠️ **2026-08-18부터 저장소가 둘이다.** `lib_copilot_a`(병합) / `lib_copilot_b`(조건부).
> 다른 파일은 `src/pipeline.py` 하나뿐이고, 아래 설명은 **A 기준**이다.
> B는 ⑥ 다음에 "082+종합서지만 놓고 판단"하는 관문을 하나 더 두고, 거기서 확신하면 끝낸다.

사서가 실제로 하는 순서를 그대로 옮겼다. **LLM은 ⑤⑦⑨ 세 곳에서만 부른다.**

```
① 책 입력                  제목 · 저자 · 082(업체번호) · 원제(있으면)
   │
   ▼
② 알라딘 보강              비어 있는 칸만 채운다 — 책소개 · 원제 · 부제
   │                       조어 제목은 이게 없으면 못 푼다
   │                       (「부린 왕자」는 제목 어디에도 '부동산'이 없다)
   ▼
③ 원제로 승계 검색         본교서지에서 원표제가 그 원제로 시작하는 책   ← 정렬표 · 3ms
   │                       번역서 제목은 출판사가 마음대로 붙지만 원제는 안 흔들린다
   ├─ 찾음  ──────────────▶ 그 번호 승계. 끝.  LLM 안 부름     예: 「바빌론 부자들의 지혜」
   └─ 못 찾음
   │
   ▼
④ 제목으로 승계 검색       제목이 입력 제목으로 시작 + 뒤가 문장부호/끝  ← 정렬표 · 5ms
   │                       느슨하게 보면 틀린 승계가 난다
   │                       (「가장 인간적인 도시」→「가장 인간적인 것들의 역사」572)
   ├─ 찾음  ──────────────▶ 그 번호 승계. 끝.  LLM 안 부름
   └─ 못 찾음  ───────────▶ ⑤로                              12권 중 11권이 여기로
   │
   ▼
⑤ LLM ① 082 정합성        082 한 번호 + 그 번호대 본교 서가 40권만 보여준다
   │                       "이 책이 이 서가에 꽂혀도 어울리나?"  → shelf_fit 1개
   │                       ⚠️ 082가 없거나 그 번호대 본교 책이 0권이면 건너뜀
   │
   ├─ shelf_fit >= THRESHOLD_1(0.92) ──▶ **082로 확정. 끝. 뒤 단계를 안 본다**
   └─ 미만
   │
   ▼
⑥ 종합서지 검색            타대학이 이 책을 몇 번으로 분류했나 (책당 약 26개 대학)
   │                       **득표 3위까지만** (동점은 다 넣는다) · 082와 같은 번호는 뺀다
   │                       ⚠️ **본교에 0권인 번호는 뺀다** — 서가를 못 읽으면 판단할 재료가 없다
   │                       번호대마다 본교 서가 40권 (주제명 절반 + 최신 절반)
   ▼
⑦ LLM ② 키워드 추출        **책 정보만** 넣는다 (약 1,000토큰)
   │                       → 검색어 3~5개. 한국어 + 영어(LCSH 표목)
   │                       ⚠️ 082 서가를 안 보여준다 — 보여주면 그 어휘로 물든다
   ▼
⑧ 키워드 검색              제목·주제명(650)에 **5개 중 2개 이상 걸린 책만**
   │                       → 청구기호로 묶어 상위 3개 · 각 서가 10권
   │                       ⑤⑥에 이미 있는 번호면 후보를 새로 안 만들고 출처 라벨만 추가
   ▼
⑨ LLM ③ 최종 판단          082 + 종합서지 + 키워드를 **한 자리에** 놓는다
   │                       머리줄에 `[출처: 종합서지 · 키워드검색]` · ⑤의 판정도 함께
   │                       → 후보별 shelf_fit·이유 + 전체 근거(notes)
   ▼
⑩ 판정  (LLM 안 부름)      1순위 shelf_fit >= THRESHOLD_2(0.82) → 바로 확정
                          미만                                 → 후보를 놓고 사서에게 넘김
```

**⑤ 게이트가 왜 0.92인가** — 1차 점수는 082의 정오와 상관이 약하다. 그 번호대에 책이
많으면 뭘 갖다 대도 어울려 보인다(케이스7은 649권짜리라 오답인데 0.90을 받았다).
Opus 시절엔 관측 최고가 0.85라 0.90이 "닫아둔 값"이었는데, terra로 갈아타니 실제로 열렸고
열리자마자 오답을 냈다. 0.92면 두 회차 모두 #9만 통과하고 그건 정답이다.
⚠️ **게이트로 확정된 건은 사서에게 안 넘어간다.** 그게 게이트의 정의지만, 그래서 이 값이
틀리면 곧바로 "틀린 채 확정"이 된다.

**⑧에서 왜 "2개 이상"인가** — 1개만 걸려도 통과시키면 흔한 낱말이 큰 서가를 통째로
끌어온다. 「게임으로 철학하기」에서 '철학' 하나가 1435권짜리 서가를 데려와 6권짜리 정답을
파묻었다. 2개로 조이면 「어느 완벽한 이중언어자」에서 경합했던 두 번호(306.446·400.42)가
나란히 1·3위로 올라온다.

자세한 배경과 설계 판단은 **[docs/design.md](docs/design.md)** 에 있다.

### 3. API 키

`.env.example`을 복사해 `.env`를 만들고 키를 넣는다. 상위 폴더의 `.env`도 자동으로 찾는다.

```bash
cp .env.example .env
```

## 알아야 할 값

흐름을 정하는 건 **LLM이 매기는 점수 하나**와 **코드가 자르는 선 둘**입니다.

### `shelf_fit` — LLM이 매기는 점수 (0.0 ~ 1.0)

"이 신규 도서가 **본교 그 번호대 서가에 꽂혀도 어울리나**"입니다. 후보 번호마다 하나씩 붙습니다.

```
1.0  그 서가 책들과 사실상 같은 성격이다
0.7  주제는 맞는데 성격(전문서/교양서, 이론/실용)이 조금 다르다
0.4  큰 갈래는 겹치지만 초점이 다르다
0.0  전혀 다른 자리다
```

⚠️ **계산값이 아닙니다.** 임베딩 유사도 같은 수식이 없어요. 후보 번호대의 본교 책
40권(제목 + 주제명·요약 등)을 LLM이 읽고 판단해 뱉는 숫자입니다. **그래서 실행마다 흔들립니다.**

⚠️ **확신도가 아닙니다.** "이 답이 맞을 확률"이 아니라 "이 자리에 어울리나"입니다.

정의는 `src/schema.py`의 `SHELF_FIT_RUBRIC`(눈금) 한 곳에 있고, 거기서 두 갈래로 모델에게
갑니다 — 프롬프트 본문(`prompts/*.txt`의 `{SHELF_FIT_RUBRIC}` 자리)과 출력 스키마의 필드
설명(`Candidate.shelf_fit`). **점수 성향을 바꾸고 싶으면 `SHELF_FIT_RUBRIC`을 고칩니다.**

### `THRESHOLD_1` · `THRESHOLD_2` — 자르는 선 두 개

`src/config.py`에 있습니다. 호출 번호와 짝이 맞습니다.

```
THRESHOLD_1 = 0.92    082 정합성 호출이 이 값 이상 → 082로 확정. 뒤 단계를 안 본다
THRESHOLD_2 = 0.82    최종 판단 1순위가 이 값 미만  → 사서에게 넘김
```

판정은 **LLM이 아니라 코드가 합니다**(`pipeline.decide_escalate`). LLM은 점수만 냅니다.
예전엔 LLM이 "넘길까"를 직접 정했는데, 그러면 기준을 못 바꿉니다 — 불린은 숫자가 아니라
이미 내려진 결정이라, 회차 기록에 "임계값이 이랬으면"에 해당하는 값이 없거든요.

**`THRESHOLD_1 = 0.92`는 0.90에서 올린 값입니다(2026-08-18).**

1차 점수는 082의 정오와 상관이 약합니다 — 그 번호대에 책이 많으면 뭘 갖다 대도 어울려
보입니다(#7은 649권짜리 서가라 오답인데 0.90을 받았습니다).

Opus 시절엔 관측 최고가 0.85라 0.90이 "닫아둔 값"이었는데, `gpt-5.6-terra`로 갈아타니
점수 분포가 올라가 게이트가 실제로 열렸고 **열리자마자 오답을 냈습니다**(#3·#5·#7).
0.92로 올리면 두 회차 모두 #9만 통과하고 그건 정답입니다.

⚠️ **게이트로 확정된 건은 사서에게 안 넘어갑니다.** 그게 게이트의 정의지만, 그래서 이 값이
틀리면 곧바로 "틀린 채 확정"이 됩니다. 표본이 4건뿐이고 terra 기준이라, 프롬프트를 고치면
다시 찾아야 합니다.

**`THRESHOLD_2 = 0.82`의 근거** (같은 조건 두 회차):

같은 책의 점수가 회차마다 **최대 0.10** 흔들립니다(#10 0.62↔0.72, #3 0.88↔0.80).
그래서 "한 회차에서 잘 드는 값"이 아니라 **두 회차 모두에서 안전한 값**이어야 합니다.

```
THRESHOLD_2   A회차 확정   B회차 확정   틀린 채 확정
   0.80          6           8        ⚠️ B에서 1건 — #12가 정확히 0.80을 찍어 오답 확정
   0.82          6           6        ✅ 없음
   0.85          5           4        ✅ 없음 (자동화만 줄어듦)
```

⚠️ **한 회차만 돌리고 이 값을 정하지 마세요.** 처음엔 1회차만 보고 0.80으로 잡았다가
두 번째 회차에서 틀린 답이 확정됐습니다.

### 튜닝하는 순서

```
① 프롬프트를 고친다     prompts/systemprompt_2nd.txt → 점수 분포가 움직임. 12건 재실행 필요
② 점수 정의를 고친다     schema.SHELF_FIT_RUBRIC      → 점수 분포가 통째로 움직임. 12건 재실행 필요
③ 서가 표본을 바꾼다     config.SHELF_SAMPLE(40권)    → 점수의 근거가 바뀜. 12건 재실행 필요
                        config.MAX_UNION_CANDIDATES(3위)
④ 자르는 선을 옮긴다     config.THRESHOLD_1 · THRESHOLD_2 → 재실행 불필요. 저장된 .json만으로 쓸어볼 수 있음
```

**④를 마지막에 하세요.** ①②③을 고치면 점수 분포가 움직여서 임계값을 어차피 다시 찾아야 합니다.
값은 환경변수로도 바뀝니다:

```bash
LIBCOPILOT_THRESHOLD_2=0.75 python3 evaluate.py --label=th075
```

## 프롬프트는 파일에 있습니다 — `prompts/`

시스템 프롬프트를 코드 밖으로 뺐습니다. **고치려고 `classify.py`를 열 필요가 없습니다.**

```
prompts/systemprompt_1st.txt      082 하나만 놓고 서가에 대보는 호출
prompts/systemprompt_keyword.txt  책 정보만 보고 검색어를 만드는 호출
prompts/systemprompt_2nd.txt      후보를 다 놓고 점수 매기는 호출  ← B는 이걸 두 번 쓴다
```

`1st` = 082 하나만 보는 호출, `2nd` = 후보 비교 호출입니다. **파일명은 ASCII로 둡니다** — 한글 파일명은 OS마다 정규화가 갈려 클론했을 때 "파일 없음"이 납니다.
1차 판정이 2차 프롬프트에 그대로 들어가므로 **둘은 한 쌍으로 움직입니다** — 한쪽만 고치면 앞뒤가 어긋납니다.

실험본은 다른 이름으로 복사해 환경변수로 지목합니다:

```bash
cp prompts/systemprompt_2nd.txt prompts/exp_min2.txt
LIBCOPILOT_PROMPT_2=prompts/exp_min2.txt python3 evaluate.py --label=min2
```

어떤 파일로 돌렸는지와 **프롬프트 전문**이 회차 md의 「이 회차 조건」에 남으므로, 나중에 그 회차를 그대로 재현할 수 있습니다.

⚠️ 프롬프트 안의 `{SHELF_FIT_RUBRIC}` 자리에는 `schema.py`의 눈금이 끼워집니다. **두 프롬프트가 같은 눈금을 쓰게 하려는 것**이니 지우지 마세요.

## 실행 파일 네 개

| | 무엇 | 산출물 |
|---|---|---|
| **`evaluate.py`** | 골든셋 12건을 돌려 **채점**한다 (정답 `expected` 필요) | `output/<회차>.md` + `.json` |
| **`run.py`** | 책 한 권을 분류하고 결과·근거를 보여준다 | 터미널 |
| **`app.py`** | 사서가 쓰는 데모 화면. 결과 + 근거 + 확정/변경 | `runs/decisions_*.jsonl` |
| **`app_for_experiment.py`** | 프롬프트 작업창. 화면에서 고치고 바로 돌려본다 | **없음** (탐색용) |

넷 다 같은 파이프라인(`pipeline.classify_book`)을 부른다. 차이는 **정답을 아느냐**와
**결과를 어디에 남기느냐**뿐이다.

`app_for_experiment.py`가 아무것도 저장하지 않는 건 일부러다 — 탐색 기록이 회차를 덮으면
"무엇이 좋아졌나"를 못 센다. 괜찮은 프롬프트는 `prompts/*.txt`에 반영하고 `evaluate.py`로
12건을 돌려 회차로 남긴다.

## 평가 결과 읽는 법

`python evaluate.py`를 돌리면 `output/`에 회차별로 두 파일이 쌓인다(덮어쓰지 않는다).

```
output/20260801-0557_clean.md      사람이 읽는 요약
output/20260801-0557_clean.json    케이스별 상세 (후보 · 근거 · 단계 귀속)
```

**채점은 책의 종류에 따라 두 갈래다:**

| 유형 | 무엇으로 채점하나 |
|---|---|
| **정답이 하나였던 책** (작성자 == 교열) | 1순위가 그 번호인가 |
| **사람도 갈렸던 책** (작성자 != 교열) | ① 경합한 두 번호를 후보에 다 담았나 ② 사서 확인이 필요하다고 표시했나 |

후자는 *맞히는* 게 아니라 **판단을 사람에게 제대로 넘기는 것**이 성공이다.

> ⚠️ **LLM 판단이라 실행할 때마다 결과가 흔들린다.** 단일 회차 숫자로 판단하지 말고, 같은 조건으로 2~3회 돌려 어떤 케이스가 고정이고 어떤 게 흔들리는지 보는 것이 맞다. 실제로 2026-08-05에 같은 조건 두 회차가 10/12와 9/12로 갈렸고 「부린 왕자」는 정답↔오답이 뒤집혔다.
