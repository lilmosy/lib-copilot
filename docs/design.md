## 1. 무엇을 푸는가

도서관에 새 책이 들어오면 사서가 **청구기호(852 ▼h)** 를 매긴다. 이 번호가 곧 책이 꽂힐 자리다.

이 일에는 성격이 다른 두 문제가 섞여 있다.

| | 무엇이 문제인가 | 어떻게 푸나 |
|---|---|---|
| **반복적이다** | 매 권마다 같은 검색을 손으로 되풀이한다 (082 확인 → 종합서지 → 본교 재확인) | **자동화한다** — 확실한 건 답 하나로 끝낸다 |
| **일관되지 않다** | 판단이 사서의 암묵지에 기대 있어 사람마다 갈린다 | **판단이 갈리는 지점에만 사람이 개입**한다 — 후보와 근거를 함께 내놓는다 |

두 번째가 실제로 얼마나 되냐면, 사서가 처리한 12권 중 **4권이 작성자가 매긴 번호를 교열 담당자가 뒤집었다**:

| 책 | 작성자 | 교열 최종 |
|---|---|---|
| 사랑받는 서점을 만들기 위해 2000일 | 658.827 (소매경영) | **381.45002** (서적판매업) |
| 어느 완벽한 이중언어자 | 400.42 (언어학) | **306.446** (사회학) |
| 부린 왕자 | 179.9 (자기계발) | **332.6324** (부동산투자) |
| 일리아스 좋아하세요? | 883 (그리스문학) | **028.9** (독서) |

둘 다 틀리지 않았다. **같은 책을 어느 관점에서 보느냐**의 문제다.

그래서 이 프로젝트의 목표는 "정답을 맞히는 기계"가 아니다:

> **쉬운 건 자동으로 끝내고, 판단이 갈리는 건만 사람에게 넘긴다.**

원천 문서(케이스 분석 docx 부록1)도 같은 말을 한다 — *"위 신호가 감지되면 단일 청구기호를 강제하지 말고 후보 + 근거를 함께 제시"*.

### 1.1 왜 ▼h 하나만 다루는가

852에는 ▼h(분류기호) 외에 ▼i(도서기호)·▼m(부가기호) 등이 붙는다. 그중 **판단이 갈리는 곳은 ▼h뿐**이고 나머지는 규칙이나 근사로 처리된다(저자기호 표, 번역서면 ▼m=K 등). 그래서 지적 난이도가 있는 ▼h 한 곳에 집중한다. 852 전체 조립은 이후 과제다.

### 1.2 시뮬레이션 전제

**실제 도서관 시스템에 붙지 않는다.** 시나리오 기반으로 개발·평가한다.

- **정답셋** — 사서가 근무 중 수기로 기록한 케이스 12건을 골든셋 JSON으로 정규화
- **DB 가정** — 업체 082를 실시간으로 받는 파이프는 만들지 않는다. 대신 *"업무 중 마주치는 책들"*(그 번호대·제목 검색으로 떠오르는 책)을 모은 장서 DB가 있다고 가정한다
- **개발 방식** — 사례 하나를 끝까지 굴리며 시행착오 → 평가를 고도화. "하/중/상을 딱 나누는 완벽한 기준"은 만들지 않는다

## 2. 사서가 실제로 하는 일

근무기록을 정리하면 이 순서다.

```
새 책이 들어온다  (제목 · 저자 · 업체가 함께 보낸 번호 082)
   │
   ├─ 이미 있는 책인가?
   │     원제로 본교 서지를 뒤진다
   │     번역서면 원서나 이전 판본이 이미 꽂혀 있을 수 있다
   │     ⇒ 있으면 그 청구기호를 그대로 쓴다. 여기서 끝
   │
   ├─ 업체가 준 번호(082)가 맞나?
   │     그 번호대에 실제로 꽂힌 책들을 본다
   │     "이 서가가 무슨 주제인가"를 책 제목·주제어로 읽는다
   │     ⇒ 이 책과 맞으면 채택
   │
   ├─ 안 맞으면 — 타대학은 이 책을 몇 번으로 분류했나?
   │     종합서지(타대학 소장목록)에서 제목으로 찾아 번호별로 센다
   │     ⇒ 이건 "정답"이 아니라 "어느 번호부터 확인해볼까"의 순서 힌트다
   │
   ├─ 그 번호들을 다시 본교에서 확인한다
   │     각 번호대에 뭐가 꽂혀 있는지 보고, 이 책 주제와 가장 맞는 자리를 고른다
   │     ⇒ 최종 결정 근거는 언제나 '본교 서가의 의미'다
   │
   └─ 확정  (애매하면 다른 사서와 상의하거나, 교열에서 뒤집힌다)
```

**핵심 규칙 두 가지**

- **본교 서지 정합성이 최우선.** 종합서지는 후보를 제안할 뿐 결정권이 없다
- **082는 출발점이지 정답이 아니다.** 주제와 맞으면 쓰고, 아니면 버린다

## 3. 이걸 시스템으로 옮기면

**LLM 호출은 두 종류뿐이다.** LLM-F(독립 shelf_fit: 책 1권 × 서가 1곳)와
LLM-K(키워드 추출). 후보를 찾고, 합치고, 정렬하고, 업무 결론을 내는 것은 전부 코드다.

```
① 책 입력                  제목 · 저자 · 082(업체번호) · 원제(있으면)
   ▼
② 알라딘 보강              비어 있는 칸만 채운다 — 책소개 · 원제 · 부제
   │                       조어 제목은 이게 없으면 못 푼다
   │                       (「부린 왕자」는 제목 어디에도 '부동산'이 없다)
   ▼
③ 원제로 승계 검색         본교서지에서 원표제가 그 원제로 시작하는 책   ← 정렬표 · 3ms
   ├─ 찾음  ──────────────▶ 그 번호 승계. 끝.  LLM 안 부름     예: 「바빌론 부자들의 지혜」
   ▼
④ 제목으로 승계 검색       제목이 입력 제목으로 시작 + 뒤가 문장부호/끝  ← 정렬표 · 5ms
   │                       느슨하게 보면 틀린 승계가 난다
   │                       (「가장 인간적인 도시」→「가장 인간적인 것들의 역사」572)
   ├─ 찾음  ──────────────▶ 그 번호 승계. 끝.  LLM 안 부름
   └─ 못 찾음  ───────────▶ 1단계로                            12권 중 11권이 여기로

【1단계】 082
   LLM-F ×1               082 번호대의 본교 서가 40권. "이 서가에 꽂혀도 어울리나?"
   │                       ⚠️ 082 번호 자체는 LLM에 안 준다(코드의 prior지 책 내용이 아니다)
   │                       ⚠️ 082가 없거나 그 번호대 본교 책이 0권이면 fit을 안 부른다
   ├─ 게이트(THRESHOLD_1)  decide.EARLY_STOP=on일 때만 실제로 멈춘다. 지금은 off —
   │                       판정만 기록하고 끝까지 간다(문턱 재산정 중)
   ▼
【2단계】 + 종합서지
   검색(코드)              타대학 득표 3위까지 (동점 포함) · 082와 같은 번호 제외(§3.1)
   │                       · 본교 0권 번호 제외 — 서가를 못 읽으면 판단 재료가 없다
   LLM-F ×N               **새로 생긴 후보에만** 1회씩. 082 점수는 1단계 것을 그대로 쓴다
   ▼
【3단계】 + 키워드
   LLM-K ×1               **책 정보만** 넣는다(약 1,000토큰) → 검색어 3~5개(한국어+영어 LCSH)
   │                       ⚠️ 서가를 안 보여준다(§3.3)
   검색(코드)              title·marc_650에 LIKE → 5개 중 2개 이상 걸린 책만(§3.4)
   │                       → GROUP BY marc_852h → 상위 후보 · 서가는 다른 후보와 같은 40권
   │                       이미 있는 번호가 또 걸리면 후보를 새로 안 만들고 출처 라벨만 추가
   LLM-F ×N               역시 새 후보에만
   ▼
판정 (LLM 0회)            decide.decide() — 점수 내림차순 정렬.
                          파일럿(AUTO_CONFIRM=off 기본): 승계 빼고 전부 사서 검토로 가고,
                          문턱(THRESHOLD_2) 통과 여부는 auto_confirm_eligible로 기록만 된다.
```

**핵심 성질 — 같은 서가는 전 과정에서 딱 한 번 평가된다.** 점수 `shelf_fit`은
`(책, 서가)` 하나의 함수다. 예전엔 후보 5~8개를 한 프롬프트에 넣고 한꺼번에 매겨서,
같은 책·같은 번호라도 옆에 누가 들어왔느냐로 점수가 달라졌고 문턱 재산정이 원리적으로
불가능했다. 독립 fit 호출에는 다른 후보·출처·득표수·단계·문턱을 **넣지 않는다**(§8-1).

**한 단계 안의 fit 호출은 동시에 나간다**(서로를 안 보므로 결과가 안 달라진다 —
`config.FIT_CONCURRENCY`). 단계 사이는 순차다.

**임계값 두 값은 재산정 중이다.** 옛 척도(비교 채점)에서 뽑은 0.92/0.82는 독립 fit
분포에서 근거가 없다 — 첫 분포 회차에서 1위 점수가 0.78~1.00에 몰려 T2=0.82가 33건 중
31건을 통과시켰다. 게이트를 연 채 분포를 쌓고 저장된 회차 json으로만 다시 정한다.
같은 회차에서 "1위 점수 하나로는 사람도 갈린 건을 못 잡는다"도 관측됐다 — 갈린 책은
두 서가 다 높은 점수를 받으므로, 신호는 1·2위 격차(gap) 쪽에 있다. gap 정책은 분포를
더 관측한 뒤 정한다.

### 3.3 왜 키워드를 별도 호출에서 뽑는가

1차 호출에 얹으면 호출이 안 늘어 싸다. 그런데 **1차는 082 서가 40권을 보고 있다.**
「게임으로 철학하기」는 082=102(철학, 649권) 서가를 보고 있어서, 거기에 검색어를 뽑으라
하면 '철학'이 나오고 검색도 193(1435권)·100(797권)으로 끌려간다.

**082가 오답인 케이스야말로 키워드 검색이 필요한 자리인데, 목적과 반대로 돈다.**
그래서 책 정보만 넣는 깨끗한 호출로 분리했다. 게이트 뒤에 두어 하 케이스에서는 안 돈다.

### 3.4 왜 "5개 중 2개 이상"인가

OR(1개만 걸려도 통과)로 두면 흔한 낱말이 큰 서가를 통째로 끌어온다.

```
#7 게임철학   1개 이상 → 193(1435권)·100(797)·194(787) …  정답 794.801(6권)이 파묻힘
#10 이중언어  1개 이상 → 306.44(146)·400.19(54) …          정답 306.446이 4위로 밀림
              2개 이상 → **306.446(17) 1위** · 400.42(3)    ← 경합 두 번호가 나란히
```

`400.42`는 종합서지 후보에 없어서 `covers_both=False`로 감점되던 작성자안이다.
필터를 조이니 랭킹은 건수순으로 충분했다 — 비율순은 3권 중 3권=100% 같은 미세 서가가
상위를 먹어 못 쓴다. 후보가 2개 미만이면 1개 이상으로 완화한다(조어 제목 대비).

**형식어 금지**가 프롬프트에서 제일 중요한 문장이다. '역사·연구·입문·history'는 주제가
아니라 책의 형식이라 대서가를 끌어온다 — 「향신료의 역사」에 '역사'를 넣는 순간
901(82권)·909(52권)에 정답이 파묻힌다.

각 단계가 왜 그 모양인지는 아래에, 시행착오는 [devlog.md](devlog.md)에 있다.

### 3.1 왜 082 득표를 종합서지에서 빼는가

1단계에서 082가 맞는지 이미 판단했다. 그런데 타대학도 같은 업체 번호를 그대로 받아 등록했을 수 있다. 그러면 **같은 증거를 두 번 세는 셈**이라, 2단계 득표에서 082 번호는 제외한다.

### 3.2 왜 비교를 LLM에서 떼어냈는가

사서는 후보를 나란히 놓고 비교한다 — 처음엔 그걸 그대로 옮겨 후보 전부를 한 프롬프트에
넣고 비교 채점을 시켰다. 그 결과 점수가 후보 집합의 함수가 됐고(§3 핵심 성질), 조기 종료
프롬프트는 082 서가의 우연한 유사서 한 권에 닫혀버리는 사고를 냈다(「가장 인간적인 도시」).

지금은 **적합도 평가(LLM, 서가 하나씩)와 비교(코드, 정렬·문턱)를 분리**한다. 업무 순서
자체는 3단계로 살아 있다 — 바뀐 건 "무엇을 LLM에게 시키나"다. 확신하며 틀리는 건을
구조로 막으려면, 확신(점수)과 결정(문턱)을 서로 다른 주체가 내야 한다.

### 4.1 책소개는 알라딘에서 받는다

당초 국립중앙도서관 API를 "근본 해법"으로 잡았으나 12권 실측 결과 아니었다:

| | 국립중앙도서관 seoji | **알라딘 TTB** |
|---|---|---|
| 책소개 | 3 / 12 | **12 / 12** |
| 목차 | 4 / 12 | 0 / 12 (별도 협의 대상) |
| 책 매칭 | 3건 오류 + 1건 미수록 | **12 / 12** |

목차가 오는 4건은 이미 잘 풀리는 책이고, 정작 필요한 책엔 안 온다. 알라딘 요약 책소개(100~220자)로 충분했다.

**분류 대상 책 한 권에만** 부른다. 서가 책 수백 권에는 부르지 않는다 — 사서도 서가를 훑을 땐 제목·주제어만 보고, 서가 책엔 이미 `일반주제명`이 절반쯤 붙어 있다.

응답은 캐시에 굳힌다. 알라딘 문구가 바뀌어도 골든셋 점수가 흔들리지 않게 하기 위해서다.

⚠️ **책소개는 양날의 검이다.** "이 책이 무엇에 관한 책인가"는 훨씬 정확히 읽게 만들지만, 그게 **도서관 배가 관행과는 멀어질 수 있다** — 「부린 왕자」 책소개의 '우화'라는 단어가 판단을 문학(811.36) 쪽으로 끌었다.

## 5. 데이터 계약 (스키마)

`src/schema.py` 한 곳에 모은다. 검색 방식을 갈아끼워도 이 계약은 안 바뀐다.
**케이스5(「가장 인간적인 도시」) 실제 데이터**로 입력부터 출력까지 따라가면 이렇다.

### 5.1 입력 — `BookInput`

파이프라인이 받는 전부. **정답 필드는 존재하지 않는다.**

```jsonc
{
  // ── 서지 기본 ── 책에 붙어 오는 정보
  "title":          "가장 인간적인 도시",              // 본표제
  "subtitle":       "실리콘밸리의 젊은 건축가가…",       // 부제. 초점을 읽는 데 크다
  "author":         "정현재",                       // 저자 (역자·원저자가 섞여 오기도 한다)
  "publisher":      null,                          // 발행처. 외부 API 매칭 검증에 쓸 수 있다
  "pub_year":       null,                          // 발행년

  // ── 업체가 준 힌트 ──
  "ddc_082":        "720.105",   // 업체가 함께 보낸 DDC. **출발점이지 정답이 아니다.**
                                 // 없을 수도 있다(그러면 2단계부터 시작)

  // ── 번역서 처리 ── 0차 승계에서 쓴다
  "is_translation": false,       // 번역서인가
  "original_title": null,        // 원제. 이게 있으면 본교에 원서·이전 판본이 있는지 먼저 뒤진다

  // ── 판단을 돕는 본문 정보 ── 있으면 정확도가 크게 오른다
  "keywords":       [],          // 주제어. 실전엔 없어서 평가에서도 비운다
  "toc":            [],          // 목차. **현재 어느 소스에서도 안 온다** (§9)
  "description":    "실리콘밸리에서 활동하는 젊은 건축가인 정현재 저자가 …"
                                 // 책소개. 알라딘이 채운다. 제목만으론 못 읽는 초점을 알려준다
}
```

### 5.2 1차 산출물 — `RetrieveResult`

검색만 한다. LLM은 아직 안 부른다. **업무 순서를 구조로 담는다.**

```jsonc
{
  "retriever": "default",     // 어느 검색기가 만들었나. 갈아끼워도 이 아래 구조는 같다

  "messages": [               // 경과를 사람 말로. 화면 '근거' 칸과 로그에 그대로 쓴다
    "082(720.105) 있음 → 본교에서 의미 확인 (본교에 해당 번호대 있음).",
    "종합서지 매칭: 「가장 인간적인 도시…」 · DDC 22개 대학(서강 1개 제외) · KDC 8개(미집계).",
    "DDC voting(순서 힌트): 720.2(14), 720.1(2), 720.285(1), 711.4(1), 720.563(1)  ※082는 제외"
  ],

  "prior_candidate": {
    "ddc_h":       "720.105",   // 후보 번호 그 자체
    "union_votes": 3,           // 타대학 득표(참고용). 2단계 목록에는 이 번호가 안 들어간다
    "shelf_count": 7,           // 본교에 이 번호대 책이 몇 권인가 — **전량이라 정확**
                                //   (부정확한 건 아래 shelf_books, 최대 40권 표본)

    "shelf_books": [            // ★ 그 번호대에 실제로 꽂힌 책들 (최대 40권)

        "detail": {             // 상세페이지 원자료 — 주제를 말해주는 건 대부분 여기 있다
          "자료유형":     "단행본",                    // 형식 정보 (주제와 무관)
          "서명/저자사항": "인공지능시대의 건축 … / Neil Leach 저 ; 송종은 옮김",

    {"ddc_h": "720.2",   "union_votes": 14, "shelf_count": 50, "shelf_books": [/* 40권 */]},
```

> 최종 판단은 `shelf_books`가 말해주는 **본교 서가의 의미**로 한다.

### 5.3 판단 산출물 — `ShelfFitAssessment` → `CandidateDecision`

LLM은 **후보 하나당 점수 하나**를 낸다(`ShelfFitAssessment` — fit 호출 하나의 결과물).
정렬·자동확정 자격·사서 이관은 코드가 정해 `CandidateDecision`으로 묶는다(`decide.py`).

왜 — 예전엔 LLM이 `escalate` 불린을 직접 냈다. 그러면 **넘기는 기준을 못 바꾼다.**
불린은 숫자가 아니라 이미 내려진 결정이라, 회차 기록에 "임계값이 이랬으면"에 해당하는
값이 없다. 점수로 받아두면 저장된 `.json`만으로 임계값을 다시 쓸어볼 수 있다(재실행 0회).

```jsonc
// ShelfFitAssessment — 후보 하나당 하나. 입력은 신규 책 + 그 번호대 서가 40권뿐이다.
{
  "h": "720.2",             // 어느 서가를 평가했나 — ⚠️ 코드가 찍는다(LLM 출력을 안 믿는다)

  "shelf_fit": 0.91,        // ★ "본교 이 번호대 서가 책들과 이 도서의 주제·성격 적합도"
                            //   확신도·정답 확률·후보 중 1위일 확률이 **아니다**
                            //   다른 후보를 보지 않고 매긴 값 — 정의는 schema.SHELF_FIT_RUBRIC 한 곳

  "shelf_label": "건축가 시선의 도시·공간 교양 비평",
                            // 표시용 서가 한 줄 요약. 점수·정렬·문턱에는 안 쓴다

  "fit_reasoning": "서가 표본은 … / 신규 도서는 … / 다만 …",
                            // 3단 구조: ①표본 전체의 중심 주제·성격 ②맞는 지점
                            // ③실제로 남는 불일치 또는 사서 확인이 필요한 보류 지점

  "cited_books": ["도시논객", "공간 인간"]
                            // 근거 도서 2~4권 — 코드가 실제 40권 표본과 대조해 통과분만 남긴다
}

// CandidateDecision — 코드가 채운다. LLM이 채우는 필드가 하나도 없다.
{
  "assessments": [ …점수 내림차순… ],
  "auto_confirm_eligible": true,   // 문턱(THRESHOLD_2) 통과 여부 — 파일럿에서는 기록만
  "escalate": true,                // 파일럿(AUTO_CONFIRM=off)에서는 승계 빼고 항상 true
  "escalate_reason": "파일럿 운영: 1순위 720.2의 서가 적합도는 0.91로 …"
}
```

**출처(082/종합서지/키워드)는 이 스키마에 없다** — LLM이 알면 안 되는 정보라서다(§8-1).
화면·회차 json은 retrieve 결과(`cand_sources`)와 번호로 조인해 표시한다.

### 5.4 화면이 이걸 어떻게 쓰나

```
승계               →  ▼h 즉시 확정 (결정론 규칙, LLM 0회)
그 외 (파일럿)      →  후보 전부 + 점수 + 근거 — 사서가 봐주세요
                      [확정] [다른 번호로: ___] · 문턱 통과 여부는 참고로 표시
```

`escalate`은 **"답을 낼지 말지"가 아니라 "사람 손을 거치느냐"** 를 정한다. 답은 언제나 낸다.
자동확정은 `AUTO_CONFIRM=on`일 때만 실제로 일어난다 — 켜는 시점은 입력·프롬프트·표본을
고정하고 top+gap 정책을 실증한 뒤다.

### 5.5 넣었다가 뺀 것들 — 다시 넣지 말 것

| 뺀 것 | 왜 |
|---|---|
| `confidence` / `ambiguity` | 프롬프트에 정의가 없어 LLM 자의로 채워지던 숫자. 흐름을 제어하지도 않았다. ⚠️ 지금의 `shelf_fit`은 다르다 — 정의가 `schema.SHELF_FIT_RUBRIC` 한 곳에 박혀 프롬프트로 들어가고, 이 값이 실제로 흐름을 정한다 |
| 1·2순위 격차 조건(`gap`) | 비교 채점 시절 한 번도 안 걸려 뺐다(점수가 인위로 벌어져 있었다). ⚠️ 독립 fit에서는 사정이 다르다 — 갈린 책은 두 서가 다 높게 나와 gap이 자연 신호가 된다(2026-08-19 관측). 분포를 더 쌓은 뒤 **관측을 근거로** 되살릴 후보다. 근거 없이 값부터 박지 말라는 원칙은 그대로다 |
| `CandidateSource` (082_kept/rejected/…) | 082 유지·기각은 `후보번호 == ddc_082`로 계산되고, 승계는 이미 플래그가 있다 |
| `signals` (cross_major 등 4종) | 원천 문서의 '상 케이스 공통 현상' 목록. **참조는 프롬프트가 시키고, 이유는 fit_reasoning이 문장으로 쓴다.** 태그로 기록해봐야 흐름을 안 바꿨다 |
| `similar_refs` | 프롬프트에 지시도 없는데 채워지던 필드. 내용이 근거 문장과 중복 |

원칙 하나로 줄이면: **시스템이 이미 아는 것은 LLM에게 묻지 않는다.**

### 5.6 서가 책은 레코드 통째로 넣는다

제목만으로는 서가 의미가 흐리다. 「건축만담」만 봐선 뭘 다루는지 모르지만 `일반주제명: Architecture, Domestic --Korea`는 바로 말해준다. 그래서 상세정보를 함께 넣는다.

⚠️ **단 `detail.분류기호`는 뺀다.** 실제 배가 위치(`ddc_h`)와 **30%가 어긋나** 있어서, 후보에 없던 번호가 상세정보를 타고 들어와 답으로 채택된 사고가 있었다 — 「주당천리」는 서가가 `641.210951`인데 분류기호 필드는 `641.2109519`다.

## 7. 평가

### 7.1 채점을 두 갈래로 나눈다

**난이도 라벨(하/중/상)은 쓰지 않는다.** 실전에는 없는 라벨이고, 무엇보다 `작성자 ≠ 교열`이 그 라벨과 12/12 일치한다 — '상'의 정의가 곧 뒤집힘이기 때문이다.

| 유형 | 조건 | 무엇으로 채점하나 |
|---|---|---|
| **정답이 하나** | `작성자 == 교열` | 1순위가 그 번호인가 (**자동 확정**을 노리는 구간) |
| **사람도 갈림** | `작성자 != 교열` | ① 경합한 두 번호를 후보에 다 담았나 ② 사서 확인이 필요하다고 표시했나 |

후자에서 "정답 하나를 맞혀라"라고 요구하면 정확도가 아니라 **이 도서관 교열 담당자의 습관을 외우라는 뜻**이 된다.

### 7.2 누출 방지

정답은 구조적으로 샐 수 없다 — **`BookInput`에 정답 필드가 존재하지 않는다.** 파이프라인은 서지 정보만 받는다.

다만 본교 DB를 같은 도서관에서 크롤했기 때문에 **평가 대상 책이 이미 장서에 있으면 정답째로 노출된다.** 그래서 조회 시점에 그 책을 동적으로 제외한다(`holdout`). 원본 json은 손대지 않는다. 데모·실전에서는 홀드아웃을 쓰지 않는다.

종합서지에서도 서강대는 항상 제외한다 — 자기 답을 베끼는 것이므로.

### 7.3 결과는 회차마다 쌓는다

LLM 판단이라 **같은 조건에서도 실행마다 결과가 흔들린다.** 그래서 산출물을 덮어쓰지 않는다:

```
output/20260801-0557_clean.md      사람이 읽는 요약 (한눈에 · 케이스별 · 못 푼 건과 대응)
output/20260801-0557_clean.json    케이스별 상세 (입력 · 후보 · 판단 근거 · 단계 귀속)
```

`--label`로 "무엇을 바꾼 회차인지" 남긴다. 같은 라벨로 2~3회 돌려야 노이즈 폭이 나오고, 라벨이 바뀌면 그게 변경 효과다.

## 8. 규약 — 손대기 전에 읽을 것

1. **LLM 호출은 `llm.ask()`를 통해서만, 부르는 곳은 `fit.py`·`keywords.py` 둘뿐.** 늘리지 않는다.
   **fit 호출에 다른 후보·출처·득표수·단계·문턱·082 번호를 넣지 않는다** — 하나라도 들어가면
   점수가 독립 적합도가 아니라 후보 비교 점수가 되어 문턱 재산정이 무너진다.
   같은 서가에 두 번 점수를 매기지 않는다(앞 단계 점수를 그대로 쓴다)
2. **저장소 접근은 `sogang_db.py` / `union_db.py`를 통해서만.** DataFrame은 그 파일 밖으로 나가지 않는다 → 나중에 SQLite로 갈아끼워도 부르는 쪽이 안 바뀐다
3. **검색기를 갈아끼워도 `RetrieveResult` 계약은 그대로.** `classify`·`pipeline`은 손대지 않는다
4. **토큰 규칙은 `tokens.py` 한 곳.** 홀드아웃(그 책 자신인가)과 종합서지 매칭(그 책이 맞나)이 같은 기준을 써야 한다 — 갈라지면 뺀 책과 찾은 책이 달라지는데 조용히 어긋나 눈치채기 어렵다
5. **평가 경로를 바꾸면 점수 원인을 알 수 없다.** 프롬프트·검색을 손댔으면 라벨을 바꿔 새 회차로 남기고 이전 회차와 대조한다
6. **크롤 데이터는 커밋하지 않는다** (`sogang_db_final.db` · `union_db.json`)
7. **결정 결과를 장서 DB에 되쓰지 않는다.** "확정된 책을 장서에 추가"는 자연스러워 보이지만 누출을 매번 새로 만드는 짓이다. 앱은 읽기 전용이다

## 9. 알려진 한계

- **종합서지를 제목만으로 조회한다** → 동명이서가 섞인다. 「향신료의 역사」 소장 64행 전부가 다른 책(장-마리 펠트 2005) 것이다. 우리 책은 Balard, Michel 2026이다. ⏳ **고치는 법은 아래에 적어둔다(미구현).**
- **서가 샘플 40권을 반반으로 나눠 뽑는다**(주제명 절반 + 최신 절반). 주제명은 옛날 책·외서에 몰려 있고 알라딘 책소개는 최신 한국책만 덮어서, 한쪽으로만 뽑으면 다른 쪽 정보를 통째로 잃는다. DB가 커지면 "어떤 40권이 뽑히느냐"가 판단을 좌우한다
- **알라딘 책소개는 한국 책만, 그것도 최근 책만 덮는다.** 서가 40권 중 실제로 받는 건 `720.2`가 29권, `883.01`은 1권이다. 양서 소스는 미정
- **종합서지 후보를 득표 3위까지로 잘랐다**(2026-08-13). 12건에선 정답을 잃는 건이 0건이지만 12건에서만 확인한 값이다
- **골든셋이 12건**이다. 한두 건이 뒤집히면 비율이 크게 움직인다
- **목차는 어디서도 안 온다.** 본교 상세페이지 0%, 국중 4/12(어려운 책엔 없음), 알라딘은 별도 협의 대상. 책소개로 대신하고 있다

### 9.1 동명이서 — 고치는 법 (⏳미구현, 2026-08-18 조사)

**ISBN은 필요 없다. 저자·출판년으로 잡힌다.** 원본 엑셀에 이미 있는데 JSON으로 옮길 때 버린 것뿐이다.

```
KERIS_종합목록_소장현황.xlsx   책제목 · 저자 · 출판사 · 출판년 · 소장대학 · 분류방식 · 분류기호 · 저자기호
                                        ↓ 변환 때 저자·출판사·출판년을 버림
data/union_db.json           book_title · control_no · university · scheme · class_no · author_mark
```

12건에 저자를 대조해보면 **향신료 1건만 걸리고 오탐 0건**이다. 출판년만 봐도 명확하다 — 11권이 2026인데 향신료만 2005.

```
일리아스   시나리오 '하길, 이준석'   ↔ 엑셀 '하길, 이준석'          2026  ok
향신료     시나리오 'Balard, Michel' ↔ 엑셀 '장-마리 펠트(Pelt)'   2005  ⚠️불일치
부린왕자   시나리오 '조훈희'         ↔ 엑셀 '조훈희'                2026  ok
```

**할 일 셋:**

1. `union_db.json`에 `author` · `pub_year` 필드를 살린다. 엑셀이 그대로 있으니 **재수집 불필요, 변환만 다시** 하면 된다.
2. `union_db.voting()`에서 입력 도서와 대조한다 — 저자는 `BookInput.author`, 출판년은 알라딘 `pub_date`가 준다.
3. **저자 토큰이 하나도 안 겹치거나 연도 차이가 크면** 득표를 후보로 쓰지 않고 `동명이서 의심 — 종합서지 보류`로 표시해 사서에게 넘긴다.

**실전 확장 때**: 종합서지를 새로 수집할 때부터 저자·출판년(가능하면 ISBN·원제)을 같이 받아둔다. `control_no`는 "이미 고른 레코드"를 가리키는 키일 뿐 **입력 도서와 같은 책인지 판정하는 재료가 아니다** — 다만 이번 오염을 발견한 건 이 번호였다(11권은 174~175로 시작하는데 향신료만 982로 시작).

**지금 당장은 손대지 않는다.** 12건 중 1건이고, 최종 판단은 본교 서가에서 하므로 결과가 버텼다(#3은 두 책이 모두 향신료 역사서라 번호대가 겹쳤다 — 운이었다).

## 11. 확장 — 따로 모듈로 붙인다 (⏳미구현, 2026-08-18 결정)

둘 다 **LLM 호출 0회 · 새 크롤 0회**다. 본 파이프라인이 이미 만들어내는 로그를 읽기만 한다.
그래서 본 기능(키워드 채널) 검증이 끝난 뒤 **별도 모듈로 붙인다.** 지금 같이 만들면
A/B 비교에 변수만 늘어난다.

**지금 해둘 준비는 각각 한 줄씩이다 — 데이터만 흘려보내면 된다.**

### 11.1 엣지케이스 일괄 재분류

사서 실무: 제도가 개편되거나 근로장학생이 대충 매기면 **1권짜리 외딴 번호**가 생긴다.
사서 인터뷰에서도 "그런 건 묶어주는 게 훨씬 낫다"고 했다.

```
트리거 — 키워드 검색의 부산물이라 공짜로 쌓인다
  ① 이 키워드로 걸린 게 1~2권
  ② 주류 후보와 대분류(앞 3자리)가 다르다      ← 306.446 옆의 306.446083은 세분일 뿐, 제외
  ③ 그 852h의 본교 총 소장이 3권 이하           ← 번호대 자체가 고립이어야 진짜 외딴섬
  → 재분류 큐에 적재 (책 id · 현재 852h · 그때의 키워드 · 주류 번호대)
```

**실행은 같은 파이프라인을 그대로 쓴다.** 딱 둘만 다르다:

```
신규 책   holdout 없음        · 082 게이트 ON   ← 하 케이스를 싸게 끝내는 게 목적
재분류    holdout = 그 책 id  · 082 게이트 OFF  ← 현상 유지를 의심하는 게 목적
```

게이트를 켜두면 "이 책 지금 자리 맞나요?"라고 물어놓고 현재 자리를 그대로 승인하고 끝난다
(기존 장서의 76%는 852h가 082와 같거나 그 세분이다). 재분류가 아무 일도 안 하게 된다.

holdout은 인자를 하나 여는 정도다 — 재분류는 레코드 id가 출발점이라 시나리오 JSON이 없다.
`shelf_books(..., exclude_ids=[...])` 처럼 id를 직접 받는 칸을 만들면 된다.

### 11.2 판단 사례 참조 (경합쌍)

발표의 차별점 "카탈로그 = 결정의 *결과* / 우리 = 결정의 *과정*"이 실물이 되는 자리다.

```
적재 — runs/pairs.jsonl 에 한 줄씩
  매 건 최종 후보 상위 2개를 쌍으로 (사서가 아무것도 안 눌러도 쌓인다)
    {"pair":["028.9","883.01"], "pair3":["028","883"],
     "book":"일리아스 좋아하세요?", "fits":[0.84,0.80], "source":"system"}

  사서가 1순위를 바꾸면 이유까지 (app.py의 「왜 바꾸셨나요」가 이미 받고 있다)
    {"pair":["306.446","400.42"], "book":"어느 완벽한 이중언어자",
     "chosen":"306.446", "rejected":"400.42",
     "reason":"언어학 이론서가 아니라 이중언어 사용자의 사회적 경험을 다룸",
     "source":"librarian"}

조회 — 새 책 판단 직후, 후보 상위 2개를 쌍으로 검색
  완전일치 + source=librarian  →  사례 카드 (무엇을 골랐나 · 왜)
  대분류 쌍(pair3)만 일치       →  "306 ↔ 400 경계는 N번 흔들렸습니다" 배지
```

**콜드스타트 대책:** 사서 결정은 드물게 쌓이지만 **시스템 경합쌍은 매 건 쌓인다.**
게다가 `union_db.json`에 이미 12건치 초기 시드가 있다 — 타대학 사서 수백 명의 판단이다.

```
일리아스     028(23) ↔ 883(13)
부린왕자     179(3)  ↔ 332(2)  ↔ 650
이중언어자   306(7)  ↔ 407     ↔ 401
야구장       796(3)  ↔ 782(4)  ↔ 781(3)
```

이 누적이 곧 **경계불안정지도**다(노드=번호대, 엣지=경합 횟수).
